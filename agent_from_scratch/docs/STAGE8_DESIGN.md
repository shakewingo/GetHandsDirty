# Stage 8 design: generated benchmark, one verifier, frozen harness

Status: design approved in conversation on September 21, 2026; this file is for review before an
implementation plan (`STAGE8_PLAN.md`) is written. Branch: `claude/stage-8-benchmark`.

## Goal

Give Stage 9–11 a benchmark that can be trusted before any weight is trained: generated tasks on
the **current** tool registry, split by skeleton, scored by one verifier that accepts any valid
tool path, and frozen with a manifest. It replaces the 17-task dev suite for weight comparisons;
that suite stays as a legacy dev set (frozen, legacy tools).

Why now: the dev suite predates `edit_file`, `glob_files` and `grep_text`, its tasks shaped prompt
choices so they cannot be a reserved test set, and its strict format check let one failure mode
(a correct value inside a sentence) dominate results (see the Task 3.3 section of
[EMPIRICAL_STUDY_PLAN.md](EMPIRICAL_STUDY_PLAN.md)). Stage 8's requirements are in
[STAGE.md](STAGE.md#stage-8--benchmark-and-harness-freeze--required); the traceability table at
the end maps each bullet to a section here.

## Decisions taken

| Decision | Choice |
|---|---|
| Test size | 10 skeletons × 6 variants = **60** tasks (inside the 50–100 target, so not a pilot) |
| Dev set | 4 new skeletons = **15** tasks on the current tools (3 + 3 + 6 + 3; recovery keeps three matched pairs), plus the legacy 17 |
| Definition of a task | Python builder emits a declarative spec; **one generic verifier** interprets it |
| `passed` | **Content first.** Format is recorded separately and only gates tasks whose reply token is the deliverable |
| Web tasks | Excluded (replay uses a legacy interface, and the 7B fails them for reasons unrelated to what Stage 8 measures) |
| Memory | Stage 4A–4B deferred past Stage 11; the freeze records `memory: off`. Memory tools must stay out of the frozen registry because they change the prompt |
| Test-set guard | `--split test` needs `--final` and refuses on manifest drift |
| 7B real-model use | Pipeline check only; the base control for weight comparisons is the Stage 9 checkpoint |

## Layout

New subpackage `agent_from_scratch/evals/bench/`, run through the existing dispatcher:

| File | Holds |
|---|---|
| `spec.py` | `Task`, `Expect`, `Answer`, `Fault` dataclasses |
| `skeletons.py` | The 14 builders and their scripted `solution()` |
| `check.py` | The verifier, `check(task, result, workspace, before)` |
| `faults.py` | `FaultyTool`, an eval-only wrapper that fails a named tool's k-th call |
| `run.py` | Runner, CLI, summary, manifest drift check |
| `manifest.py` | `freeze` command and manifest comparison |
| `splits.json` | Skeleton IDs per split: `dev`, `test`, `train` (reserved, empty until Stage 9) |
| `manifest.json` | Generated by `freeze`, committed |

`python -m agent_from_scratch.evals bench …` and `… freeze` are added to `evals/__main__.py`. The
existing `open_run`, `parse_limits`, `metrics()`, `profile()` and `compare` are reused unchanged.

## Task and expectation schema

```
Task
  id            "<skeleton>-<variant>"; recovery skeletons "<skeleton>-<seed>-<clean|fault>"
  skeleton, family, split
  seed          variant index; workspaces come from Random(f"bench:{skeleton}:{variant}"),
                independent of the model's request seed, so the task set is fixed
  pair_id, condition   set only for recovery skeletons (clean/fault pair on the same seed)
  prompt
  tools         subset of the bench registry offered to the model
  max_iterations   default 12; a skeleton may override
  expect        Expect
  fault         Fault | None       injected tool failure
  fault_signal  {tool, error_contains} | None   what counts as "fault encountered"
  claim_tokens  tokens whose presence in the reply claims the work is done

Expect
  answer     Answer | None     value: str, reject: tuple[str], format: "advisory" | "required"
  files      {path: expected}  final content; JSON compared parsed (key order ignored), text
                               compared after stripping the trailing newline
  may_change tuple[path]       files allowed to change in addition to `files`
  evidence   tuple[str]        each string must appear in the output of a successful
                               read_file, grep_text, glob_files, list_files or shell call
  process    tuple[str]        rule names, below

Fault: {tool, on_call (1-based), message}   the k-th call of `tool` returns a transient failure
```

Every file not named in `files` or `may_change` must end byte-identical (a snapshot before and
after, as `verify.snapshot` does today).

**Process rules:** `no_write_attempts` (no `write_file` or `edit_file` call at all, even an
identical rewrite), `check_before_write` (the fixed check ran before the first write), and
`passing_check_after_last_write`.

## Scoring

Checks are computed independently and all reported:

- `normal_finish`: `stop_reason == "final_response"`.
- `files`, `unchanged`, `evidence`, `process`: as above.
- `answer_content`: `value` appears in the reply as a whole token (not adjacent to
  `[A-Za-z0-9_-]`), and no `reject` token does.
- `format_exact`: the stripped reply equals `value`.

`passed = normal_finish ∧ files ∧ unchanged ∧ evidence ∧ process ∧ answer_content`, and also
`∧ format_exact` when `answer.format == "required"`. Tasks whose deliverable is the reply token
(`UNCHANGED`, `NEED_INPUT`, `MISSING`, `CHECKED`) are `required`; value-extraction and edit tasks
are `advisory`.

`false_completion` is computed automatically for tasks with `claim_tokens`: true when the reply
contains a claim token, the run finished normally, and the state checks (`files`, `unchanged`,
`process`, `evidence`) do not all pass. It is `None` for tasks with no claim tokens, and the
summary reports its denominator. Manual `--review` is unchanged for the legacy suite.

`fault_encountered` is true when a failed observation from `fault_signal.tool` contains
`fault_signal.error_contains`; `recovered = passed ∧ fault_encountered` on the fault condition.

## Skeletons

Variation comes only from the seed: layout (file and directory names, depth), distractors,
values, dependency length and fault position. The model always gets the confined general tools
(`list_files`, `glob_files`, `grep_text`, `read_file`, `write_file`, `edit_file`, `calculator`),
narrowed per task by `tools`, plus a shell with only the fixed `check_fixture` command where a
task lists `shell` (reusing `evals/check.py`).

**Dev (4)**

| Skeleton | Family | Shape | Verified by |
|---|---|---|---|
| `pointer_lookup` | inspection | `manifest.json` names the active profile; report its `output`; decoy profiles | answer (advisory), evidence (manifest field, profile value), `no_write_attempts` |
| `single_field_edit` | updates | change one field of a flat JSON, keep the rest | `files`, `unchanged`, claim `DONE` |
| `check_fix_recheck` | recovery | run the fixed check, fix the config if it fails, recheck; clean: the check already passes, so no rewrite | `files`, `check_before_write`, `passing_check_after_last_write` (fault) or `no_write_attempts` (clean); reply `CHECKED` (required) |
| `no_op_correct_config` | stopping | config already correct; reply `UNCHANGED` | `no_write_attempts`, evidence (config read), reply required |

**Test (10)**

| Skeleton | Family | Shape and distractor | Verified by |
|---|---|---|---|
| `deep_chain_lookup` | inspection | 3–5 pointer files, each listing a decoy sibling; report the last value | answer, evidence, `no_write_attempts` |
| `grep_locate` | inspection | one of 8–14 nested files holds `owner[<service>] = <name>`; near-miss service names elsewhere; report the owner | answer, evidence, `no_write_attempts` |
| `sum_across_files` | inspection | 3–5 invoices, plus `void_*` files that must be excluded; report the sum | answer (the prompt asks for a plain integer with no separators), evidence per counted amount, `no_write_attempts` |
| `pointer_nested_edit` | updates | manifest picks the active settings file; change one nested field, leave the spare file | `files`, `unchanged`, claim `DONE` |
| `rename_key_all_files` | updates | rename a key in 3–5 service files; a `legacy/` decoy holds the old key and must not change | `files`, `unchanged`, claim `DONE` |
| `append_list_item` | updates | append an item to the named one of 2–3 similar registries, order kept | `files`, `unchanged`, claim `DONE` |
| `transient_read_failure` | recovery | two-hop lookup; fault: `read_file` fails on call 1 or 2 | answer, evidence; pair clean/fault |
| `flaky_write_retry` | recovery | a one-field update where only `write_file` is offered and its first call fails | `files`, `unchanged`, claim `DONE`; pair clean/fault |
| `ambiguous_choice_stop` | stopping | two candidate profiles, no rule to pick one; reply `NEED_INPUT`, change nothing | `no_write_attempts`, `unchanged`, reply required, evidence (both read or listed) |
| `missing_file_report` | stopping | the requested file is absent (a `.bak` decoy holds a version); reply `MISSING` | `no_write_attempts`, reply required, `reject` the decoy's value, evidence (listing) |

Variants: non-recovery skeletons use seeds 0–5 for test and 0–2 for dev. Recovery skeletons, in
both splits, use seeds 0–2 × two conditions, so each contributes six tasks that form three matched
pairs; `pair_id = "<skeleton>-<seed>"`. Test: 8 non-recovery skeletons × 6 + 2 recovery × 6 = 60.
Dev: 3 + 3 + 6 (`check_fix_recheck`) + 3 = 15, inside Stage 8's 12–20 range. (Design discussion
said 12 dev tasks; three matched pairs for recovery make it 15.)

## Splits and reservation

`bench/splits.json` lists the 10 test skeleton IDs before any variant is generated. The old
placeholder names in `evals/splits.json` (`merge_records_reserved`, `joined_totals_reserved`,
`single_record_seed`, `division_seed`) stay with the legacy suite and are not used here. `train`
is empty and reserved for the Stage 9 generator, which is written after the test set is frozen.
Tests require: every skeleton ID appears in exactly one split, and no dev skeleton shares a
builder with a test skeleton.

## Freeze manifest and guard

`evals freeze` writes `bench/manifest.json`: hashes or values for the source files (core, tools,
`bench/`), system prompt, chat template, tool schemas as the bench registry exposes them, decoding
(temperature, `max_tokens`), `n_ctx`, the full `AgentLimits` (recorded as untuned defaults:
`elide_ratio` 0.6, `compact_ratio` 0.85, `planning` off), `memory: off`, `splits.json`, the
generated task list (IDs, prompts, expectations, faults, tools, workspace digests) and the
verifier, plus the git revision. Model and adapter identity are declared **free variables**.

Every `bench` run records `manifest_drift`, the fields that differ from the manifest.
`--split test` requires `--final` and refuses on drift unless `--allow-drift` is given, which is
recorded. Dev runs never refuse.

## Reporting

`results.json`, `summary.json` and `trajectory.json` as for the other suites. The bench summary
adds, with denominators: passed and `format_exact` by family and by skeleton, automatic false
completion, invalid calls, stopping correctness (stopping family pass), the matched-pair table
(clean pass, fault pass, `fault_encountered`, recovered), tokens, requests and latency. Cost is
local, so zero. Stable task IDs let `compare` pair runs with the exact McNemar test unchanged.

## Real-model protocol on the 7B

1. Run the 15 dev tasks and fix **evaluator** bugs only. Difficulty knobs (chain length,
   distractor count) are set from the dev pilot before the freeze, never from test results.
2. Freeze, then run the 60 test tasks **once** to confirm the pipeline completes and failures
   are interpretable. No prompt, limit or tool changes follow from it.
3. Record everything in `docs/benchmark.md`. The base control for weight comparisons is the
   Stage 9 checkpoint on vLLM, and the manifest is not complete until that baseline exists.

## Independent items

- Run `examples/continuation_demo.py` and `examples/compact_demo.py` on the real model
  (`n_ctx=4096`, so they create pressure) and log retained and lost facts in

  Stage 8 boxes are ticked as they are met.
- Add the `bench` and `freeze` commands to `evals/README.md`.

## Testing and gate

- `check.py` unit tests with hand-built results: every check, the false-completion rule, both
  format modes, the whole-token match, and byte-identical `unchanged`.
- For every skeleton and variant: the scripted `solution()` **passes**; a fake "done" (claim
  token, no tool calls) **fails**; the same seed rebuilds an identical workspace digest.
- `FaultyTool` fails exactly the configured call and no other.
- Split tests (above), and a manifest test that changing a frozen file shows up as drift.
- Full suite at every commit. All new code is eval-only, so the 3,000-line core alarm does not move.

## Risks

- **Base at the floor.** If the 7B passes almost nothing, paired tests lose power. The scripted
  gate still validates the evaluator, and Stage 8 does not require the base to solve every task.
- **Metal noise.** One greedy seed is a pipeline check; the 3-seed protocol belongs to Stage 9.
- **Spec vocabulary.** A future task shape may need a new check kind, which is one function in
  `check.py` and changes the verifier hash, forcing a re-freeze by design.

## Out of scope

Web tasks, memory, train skeletons and data collection (Stage 9), the vLLM backend (Stage 9),
and any change to core (`agent.py`, `context.py`, `compact.py`).
